## למה יחד? הקשר בין שני חצאי המפגש

*(משך משוער: 5 דק')*

עד מפגש 5 עבדנו עם AI בעיקר בצורת שיחה: אתם מבקשים, הכלי מציע, אתם מעתיקים ומריצים. במפגש הזה עוברים למשהו שונה מהותית — **agent** שפועל בעצמו על הפרויקט: קורא קבצים, כותב קוד, מריץ פקודות, ולפעמים מתקן את עצמו — הכול בלי שאתם מעתיקים דבר ידנית.

זו קפיצה גדולה ביכולת. אבל יש לה מחיר: אם agent מבצע עשרות שינויים ברצף על הקוד שלכם, איך יודעים מה בדיוק השתנה? איך חוזרים אחורה אם השינוי ה-15 שבר משהו שעבד בשינוי ה-10? התשובה היא **Git** — מערכת בקרת גרסאות שנותנת לכם "נקודות שמירה" (commits) שאפשר לחזור אליהן, להשוות ביניהן, ולהבין מי שינה מה ולמה.

לכן שני חצאי המפגש הם לא שני נושאים נפרדים באותה הרצאה — הם זוג שמשלים זה את זה: **Agent נותן לכם מהירות; Git נותן לכם רשת ביטחון בשביל להשתמש במהירות הזו בלי להתרסק.** בלי Git, עבודה עם agent על פרויקט אמיתי היא כמו לנסוע מהר מאוד בלי חגורת בטיחות.

## חלק א' — Agentic Coding

### א.1 מהו Agent?

*(משך משוער: 8 דק')*

**הגדרה:** Agent הוא כלי AI שלא רק *מציע* טקסט או קוד, אלא **מבצע פעולות בפועל** בסביבת העבודה שלכם — קורא קבצים, כותב אליהם, מריץ פקודות בטרמינל, ובודק את התוצאה — הכול בתוך לולאה אחת, לרוב בלי שאתם מאשרים כל צעד בנפרד.

ההבדל מ-Chat (שלמדנו במפגש 5) הוא לא באיכות התשובות — הוא **ביכולת לפעול**. צ'אט אומר לכם מה לעשות; agent עושה את זה בעצמו.

> **דוגמה מוחשית — אותה בקשה, שני סוגי כלים:**
>
> **בצ'אט:** "יש לי באג בפונקציה `calculate_total` — היא לא מחשבת מע\"מ נכון."
> → הכלי עונה בטקסט: "הבעיה כנראה בשורה שמכפילה ב-0.17 במקום 1.17. הנה התיקון: `total = subtotal * 1.17`". **אתם** מעתיקים את זה, מוצאים את הקובץ, מדביקים, שומרים, מריצים.
>
> **עם Agent:** אותה בקשה בדיוק. ה-agent **בעצמו**: פותח את הקובץ הרלוונטי, מאתר את השורה, עורך אותה, שומר, ולעיתים גם מריץ את הטסטים כדי לוודא שהתיקון לא שבר משהו אחר — ומדווח לכם בסוף: "תיקנתי את השורה ב-`billing.py`, הרצתי את הטסטים, כולם עברו."
>
> באותה בקשה, בצ'אט ביצעתם 4 פעולות ידניות; עם agent — אפס.

**כלל אצבע:** Agent הוא לא "צ'אט חכם יותר" — הוא כלי שסוגר את הפער בין "לדעת מה לעשות" ל"לעשות את זה בפועל".

### א.2 לולאת ה-Agent: Plan → Act → Observe

*(משך משוער: 12 דק')*

איך agent בעצם עובד? הוא רץ בלולאה חוזרת של שלושה שלבים:

1. **Plan (תכנון)** — המודל מחליט מה הצעד הבא הנדרש כדי להתקדם לעבר המטרה.
2. **Act (פעולה)** — הוא מבצע את הצעד בפועל: קורא קובץ, כותב קוד, מריץ פקודה.
3. **Observe (תצפית)** — הוא בוחן את התוצאה של הפעולה (הצליחה? נכשלה? מה הפלט?).

ואז — **חוזר לשלב 1**, הפעם עם מידע נוסף מהתצפית. הלולאה נמשכת עד שהמשימה הושלמה, או עד שה-agent "נתקע" ומבקש עזרה.

> **דוגמה מוחשית — משימה: "הוסף בדיקת קלט לפונקציה `divide(a, b)` שתמנע חלוקה באפס":**
>
> | סבב | Plan | Act | Observe |
> |---|---|---|---|
> | 1 | "קודם אמצא את הפונקציה" | קורא את הקובץ `math_utils.py` | מוצא את `divide` בשורה 12 |
> | 2 | "אוסיף בדיקת `if b == 0`" | עורך את הקובץ, מוסיף את הבדיקה | השינוי נשמר |
> | 3 | "אוודא שזה לא שבר טסטים קיימים" | מריץ `pytest` | טסט אחד נכשל: `test_divide_negative` |
> | 4 | "אבדוק למה הטסט נכשל" | קורא את קובץ הטסט | מגלה שהטסט ציפה לשגיאה אחרת מזו שהוחזרה |
> | 5 | "אתקן את הודעת השגיאה כדי שתתאים" | עורך שוב | מריץ טסטים — כולם עוברים, מדווח לכם |

שימו לב: הלולאה **לא ליניארית** — סבב 3 גילה בעיה שלא היה צפוי מראש (הטסט הקיים), וה-agent הגיב אליה בעצמו בסבבים 4-5. זו בדיוק העוצמה של הלולאה: היא מאפשרת לטפל בהפתעות תוך כדי תנועה, בלי שתצטרכו להתערב בכל שלב.

**חיבור למפגש 2:** זכרו שהמודל בעצמו הוא "רק" מנבא-טוקן-הבא. הלולאה הזו היא מה שהופך ניבוי טוקנים בודד ליכולת לבצע משימה שלמה, רב-שלבית — ע"י כך שבכל סבב המודל מקבל הקשר טרי (מה קרה בפעולה הקודמת) ומחליט מחדש מה הצעד הבא.

**מלכודת נפוצה:** לצפות שה-agent "יידע" מראש את כל התוכנית. בפועל, ה-agent מגלה חלק מהבעיות **תוך כדי** הלולאה (כמו הטסט שנכשל בדוגמה) — זו לא חולשה, זו בדיוק איך שהלולאה אמורה לעבוד. אל תתפלאו אם agent "משנה כיוון" באמצע משימה.

### א.3 Tool Use — איך ה-Agent בכלל "פועל"

*(משך משוער: 10 דק')*

מודל שפה, כזכור, יודע רק לייצר טקסט. אז איך הוא "קורא קובץ" או "מריץ פקודה" בפועל? התשובה: **tool use** (נקרא גם function calling) — המודל מקבל רשימה של "כלים" זמינים (למשל `read_file`, `write_file`, `run_command`), וכשהוא רוצה לבצע פעולה, הוא לא כותב טקסט חופשי — הוא מייצר קריאה מובנית לכלי, בפורמט קבוע (למשל JSON), עם הפרמטרים הרלוונטיים. סביבת ה-agent מזהה את הקריאה, **מריצה אותה בפועל** במחשב שלכם, ומחזירה את התוצאה למודל כטקסט — שמשמש כ"תצפית" (Observe) לסבב הבא בלולאה.

> **דוגמה מוחשית — מה שקורה "מתחת למכסה המנוע" כשה-agent קורא קובץ:**
>
> ```text
> 1. המודל מייצר (לא כטקסט חופשי, אלא כקריאת-כלי מובנית):
>    { "tool": "read_file", "path": "billing.py" }
>
> 2. סביבת ה-agent מריצה בפועל: פותחת את הקובץ billing.py, קוראת את תוכנו.
>
> 3. סביבת ה-agent מחזירה למודל את תוכן הקובץ כטקסט:
>    "def calculate_total(subtotal): return subtotal * 0.17"
>
> 4. המודל "רואה" את הטקסט הזה כהמשך השיחה, ומחליט על הצעד הבא —
>    למשל קריאת כלי נוספת: { "tool": "write_file", "path": "billing.py", ... }
> ```
>
> מבחינת המודל, זה עדיין "רק" ניבוי טוקנים — אבל הטוקנים האלה מפורשים כפקודה שרצה בעולם האמיתי, לא רק כטקסט לקריאה.

**זכרו ממפגש 5:** קריטריון "אמינות Tool-Calling" בדיוק בודק את זה — האם המודל קורא לכלי הנכון, עם הפרמטרים הנכונים, ומדווח בכנות אם הפעולה נכשלה. tool use הוא הבסיס הטכני שקריטריון האמינות שלמדנו במפגש הקודם בכלל בודק.

**מלכודת נפוצה:** לחשוב שה-agent "מבין" את הקובץ כמו בן אדם. בפועל, הוא רואה טקסט (תוכן הקובץ) ומגיב לו באותו אופן שהוא היה מגיב לכל טקסט אחר — כולל הסיכון להזיה (מפגש 2) אם הוא "בטוח" לגבי משהו שהוא לא באמת ראה.

### א.4 ספקטרום האוטונומיה — יישום מעשי

*(משך משוער: 10 דק')*

במפגש 5 הגדרנו את קריטריון "רמת אוטונומיה" כספקטרום: מ**מציע בלבד** (אתם מעתיקים), דרך **חלקי** (מבצע אך ממתין לאישור), ועד **מלא** (פועל ומתקן את עצמו בלולאה, בלי לעצור). עכשיו, כשאנחנו בפועל עובדים עם agent, השאלה הזו הופכת למעשית ביותר: **באיזו רמת אוטונומיה כדאי לעבוד ברגע נתון?**

| רמת אוטונומיה | מה קורה | מתי מתאים |
|---|---|---|
| **אישור על כל צעד** | ה-agent מציע כל שינוי, אתם מאשרים לפני שהוא נשמר | פרויקט קריטי, קוד שאתם עדיין לומדים, שלבים ראשונים עם agent חדש |
| **אישור על צעדים "מסוכנים" בלבד** | שינויי קוד רגילים עוברים אוטומטית; מחיקת קבצים / שינויי מבנה גדולים דורשים אישור | עבודה שוטפת על פרויקט מוכר, אחרי שצברתם אמון בכלי |
| **ריצה עצמאית מלאה** | ה-agent פועל בלולאה שלמה בלי עצירה, כולל תיקון עצמי | משימות שגרתיות, מוגדרות היטב, עם רשת ביטחון חזקה (טסטים + Git!) |

> **דוגמה מוחשית — אותה משימה, שתי רמות אוטונומיה:**
>
> **משימה:** "נקה את כל קבצי ה-`.log` הישנים מהפרויקט ותעדכן את ה-`.gitignore`."
>
> - **ברמת אישור-על-כל-צעד:** ה-agent מציג "אני עומד למחוק 14 קבצים: [רשימה]. לאשר?" — אתם קוראים את הרשימה, מאשרים.
> - **ברמת ריצה עצמאית:** ה-agent פשוט מוחק ומעדכן, ומדווח בסוף "מחקתי 14 קבצי לוג, עדכנתי .gitignore". אם בטעות היה שם קובץ log שדווקא רציתם לשמור — כבר מאוחר מדי, **אלא אם יש לכם Git** (ואז: `git revert`, וחזרתם אחורה).

זו בדיוק הנקודה: **ריצה עצמאית מלאה היא בסדר גמור — בתנאי שיש רשת ביטחון.** וזו הסיבה שהחלק השני של המפגש, Git, הוא לא "נושא נפרד" אלא בדיוק מה שהופך אוטונומיה גבוהה לבטוחה.

**כלל אצבע:** התחילו ברמת אישור גבוהה עם כל כלי/פרויקט חדש. הורידו את רמת הפיקוח בהדרגה ככל שאתם צוברים אמון בכלי **ובעצמכם** (ביכולת שלכם לזהות בעיה ולתקן אותה מהר).

## חלק ב' — Git מאפס

### ב.1 למה בכלל Git?

*(משך משוער: 5 דק')*

דמיינו שאתם עובדים על פרויקט עם agent ברמת אוטונומיה גבוהה. הוא מבצע 20 שינויים ברצף. בשינוי ה-14 הוא "משפר" פונקציה — אבל בפועל שובר משהו שעבד. אתם מגלים את זה רק בשינוי ה-20. **בלי Git, אין דרך לחזור בדיוק לאיך שהקוד נראה לפני שינוי 14** — הכול מעורבב יחד בקובץ הנוכחי.

**Git הוא מערכת שיוצרת "נקודות שמירה"** (commits) לאורך זמן — כל אחת היא תמונת-מצב מלאה של הפרויקט ברגע נתון. אפשר תמיד לחזור לכל נקודת שמירה, להשוות בין שתיים, ולדעת בדיוק מה השתנה ומתי.

זה בדיוק העיקרון של "מתכנת ג'וניור מוכשר" ברמת הפרויקט כולו: אתם *סומכים* על ה-agent שיעשה עבודה טובה ברוב הזמן, אבל שומרים תמיד דרך "לחזור אחורה" אם הוא טעה.

### ב.2 המושגים הבסיסיים: Repository, Commit, Branch, Merge

*(משך משוער: 20 דק')*

**Repository (בקיצור "repo")** — תיקיית הפרויקט, ברגע שהיא "מנוהלת" ע"י Git. יוצרים אחת בפקודה:

```bash
git init
```

מרגע זה, Git עוקב אחרי כל שינוי בקבצים בתיקייה הזו (עד שתגידו לו לעצור, למשל ב-`.gitignore`).

**Commit** — נקודת שמירה. "תמונת מצב" של כל הפרויקט ברגע נתון, עם הודעה קצרה שמסבירה מה השתנה. יוצרים commit בשני שלבים:

```bash
git add tasks.py          # מסמנים אילו שינויים ייכנסו ל-commit הבא
git commit -m "הוספת פונקציית delete_task"   # יוצרים את נקודת השמירה
```

> **דוגמה מוחשית — למה ההפרדה בין `add` ל-`commit` שימושית:**
>
> נניח שינית שני קבצים בלי קשר זה לזה: `tasks.py` (הוספת פיצ'ר) ו-`notes.txt` (הערות אישיות לעצמכם, לא לפרויקט). אתם רוצים ש-commit יכיל רק את `tasks.py`:
>
> ```bash
> git add tasks.py        # רק tasks.py "מוכן" לשמירה
> git commit -m "הוספת delete_task"   # ה-commit מכיל רק את tasks.py
> ```
>
> `notes.txt` נשאר "לא שמור" — הוא עדיין קיים בתיקייה שלכם, אבל לא נכנס להיסטוריה של הפרויקט. בדיוק כמו שרוצים.

**Branch (ענף)** — קו התפתחות נפרד של הפרויקט. ברירת המחדל היא ענף בשם `main`. כשרוצים לנסות משהו בלי לסכן את הגרסה היציבה, יוצרים ענף חדש:

```bash
git branch add-search-feature     # יוצרים ענף חדש
git checkout add-search-feature   # עוברים לעבוד עליו
# (או בפקודה אחת: git checkout -b add-search-feature)
```

עכשיו כל commit חדש נכנס ל-`add-search-feature`, ו-`main` נשאר בדיוק כפי שהיה — נקי ויציב.

**Merge (מיזוג)** — כשהפיצ'ר בענף החדש מוכן ועובד, ממזגים אותו בחזרה ל-`main`:

```bash
git checkout main
git merge add-search-feature
```

> **דוגמה מוחשית — תרחיש מלא, למה זה חשוב דווקא עם agent:**
>
> מבקשים מה-agent "תוסיף פיצ'ר חיפוש מטלות לפי מילת מפתח — זה ניסיוני, אני לא בטוח שאני רוצה את זה." יוצרים ענף `try-search`, נותנים ל-agent לעבוד שם. אם התוצאה טובה — ממזגים ל-`main`. אם לא — פשוט מוחקים את הענף (`git branch -D try-search`), ו-`main` אף פעם לא נגע. ה-agent יכול "להתנסות" בלי שום סיכון לגרסה היציבה.

**היסטוריה** — כל ה-commits, לפי סדר כרונולוגי, נשמרים וזמינים לצפייה:

```bash
git log --oneline
```

```text
a3f9c21 הוספת פונקציית delete_task
7b2e410 תיקון באג בטיפול ברשימה ריקה
1c8d903 הוספת פונקציית add_task
f0a1234 קומיט ראשוני
```

**כלל אצבע:** אם אתם מהססים לתת ל-agent אוטונומיה גבוהה — הפתרון הראשון הוא לא "לצמצם אוטונומיה", אלא **לעבוד בענף נפרד**. תנו לו לעבוד חופשי שם; רק מה שאתם בעצמכם מאשרים ומוזגים חוזר ל-`main`.

---

### ב.3 Commit Messages משמעותיים — גם (ובמיוחד) עם Agent

*(משך משוער: 8 דק')*

הודעת commit גרועה: `"fix"`, `"update"`, `"changes"`. הודעת commit טובה מסבירה **מה** השתנה **ולמה**, בקצרה, כך שגם אתם וגם ה-agent (בפעם הבאה) יכולים להבין את ההיסטוריה בלי לקרוא כל שורת קוד מחדש.

> **דוגמה מוחשית — אותו שינוי, שתי הודעות:**
>
> ```text
> גרוע:   "fix"
> טוב:    "תיקון: delete_task זרקה שגיאה על אינדקס שלילי — עכשיו בודקת טווח תקין"
> ```
>
> ההודעה הטובה עונה על שלוש שאלות בלי לפתוח את הקוד: מה היה שבור, איך זה בא לידי ביטוי, ומה הפתרון.

**עם agent, זה קריטי במיוחד:** אם agent מבצע 20 commits ברצף עם הודעות כמו `"update"` עשרים פעם, ההיסטוריה חסרת תועלת — אי אפשר לדעת מה קרה בלי לחפור בקוד. **בקשו מפורשות מה-agent לכתוב הודעות commit ברורות** — זה בדיוק סוג הדרישה שנכנסת לקובץ הנחיית הפרויקט שלמדנו במפגש 4 ("כל commit מקבל הודעה שמסבירה מה ולמה, לא רק 'update'").

---

### ב.4 שימוש ב-AI לתיאור PR ולסקירת קוד

*(משך משוער: 12 דק')*

**Pull Request (PR)** הוא בקשה למזג ענף (branch) לתוך ענף אחר — בדרך כלל `main` — יחד עם תיאור של מה השתנה ולמה, כדי שמישהו (אתם, או חבר לצוות) יוכל לסקור לפני שהמיזוג קורה בפועל.

AI מצוין בכתיבת תיאורי PR — כי יש לו גישה לכל ה-diff (ההבדל המדויק בין הענפים), ויכול לסכם אותו בבירור:

> **דוגמה מוחשית — פרומפט לכתיבת תיאור PR:**
>
> ```text
> "הנה ה-diff בין הענף add-search-feature ל-main.
> כתוב תיאור PR קצר: מה נוסף, למה, ואיך לבדוק שזה עובד."
> ```
>
> **תשובה טיפוסית:**
> ```text
> ## הוספת חיפוש מטלות לפי מילת מפתח
>
> **מה השתנה:** נוספה פונקציה search_tasks(tasks, keyword)
> ב-tasks.py, וכפתור חיפוש בממשק ב-main.py.
>
> **למה:** בקשת משתמש — קשה למצוא מטלה ברשימה ארוכה.
>
> **איך לבדוק:** הריצו python main.py, הקלידו "search",
> בדקו שמטלות עם ההתאמה מוצגות ואחרות לא.
> ```

ה-AI יכול גם לסייע **בסקירת הקוד עצמו** — לא כתחליף לביקורת אנושית (זוכרים את עקרון-העל!), אלא כשלב ראשון שמאתר בעיות נפוצות לפני שאתם משקיעים זמן:

> **דוגמה מוחשית — פרומפט לסקירה ראשונית:**
>
> ```text
> "סקור את הקוד הזה כאילו אתה reviewer בצוות: type hints חסרים?
> מקרי קצה לא מטופלים? שמות לא ברורים? תן רשימה קצרה, לא לתקן בעצמך."
> ```

**כלל אצבע:** AI כותב טיוטת PR description וסקירה ראשונית — **אתם** קוראים, מתקנים אם צריך, ומאשרים לפני המיזוג בפועל. בדיוק כמו כל תוצר AI אחר בקורס.

**מלכודת נפוצה:** למזג PR רק כי תיאורו נשמע טוב. תיאור ה-PR מתאר את הכוונה — לא מוכיח שהקוד עובד. תמיד להריץ ולבדוק בפועל (מפגש 8-9) לפני מיזוג.

---

## סיכום

*(משך משוער: 5 דק')*

1. **Agent** = כלי שפועל בפועל (לא רק מציע), דרך לולאת **plan → act → observe** שחוזרת על עצמה.
2. **Tool use** הוא המנגנון הטכני שהופך ניבוי-טוקנים לפעולה אמיתית בעולם — קריאה ל"כלי" מובנה שסביבת ה-agent מריצה.
3. **רמת אוטונומיה** היא בחירה מודעת — לא תכונה קבועה של הכלי; מתחילים גבוה בפיקוח, מורידים בהדרגה.
4. **Git** נותן רשת ביטחון: `commit` = נקודת שמירה, `branch` = ניסוי מבודד, `merge` = שילוב בחזרה, `log` = היסטוריה מלאה.
5. **commit messages ברורים + AI לתיאור PR/סקירה** הופכים את ההיסטוריה לשימושית וניתנת לביקורת — גם כשרוב הקוד נכתב ע"י agent.
6. **הקשר המאחד:** Git הוא מה שהופך אוטונומיה גבוהה לבטוחה — בלעדיו, אוטונומיה גבוהה היא סיכון; איתו, היא כלי עבודה יעיל.

## תרגול עצמאי (45 דקות)

**מטרה:** להריץ agent על משימה רב-שלבית תוך פיקוח, לתעד כל שלב כ-commit משמעותי, וליצור PR מדומה עם תיאור וסקירה בעזרת AI.

**כלים נדרשים:** כלי agent חינמי (למשל Claude Code בגרסה חינמית, או כל CLI Agent אחר מהרשימה במפגש 5), Git מותקן מקומית, חשבון GitHub חינמי (לא חובה לדחוף בפועל — אפשר לעבוד מקומית).

**פרויקט:** ממשיכים על ה-Todo App המוכר (מפגשים 3-4).

### שלב 1 — הקמה (5 דק')
ודאו ש-Git מותקן (`git --version`), ושיש לכם repo מקומי עם ה-Todo App (או `git init` על תיקייה חדשה עם הקבצים הקיימים מ-`main.py`, `tasks.py`).

### שלב 2 — יצירת ענף וריצת Agent מפוקחת (15 דק')
```bash
git checkout -b add-priority-feature
```
בקשו מה-agent: *"הוסף לTodo App שדה 'עדיפות' (גבוהה/בינונית/נמוכה) לכל מטלה, כולל אפשרות למיין לפי עדיפות. עבוד ברמת אישור-על-כל-צעד."*
עקבו אחרי הלולאה (Plan → Act → Observe) — שימו לב איפה ה-agent "משנה כיוון" אם הוא נתקל בבעיה.

### שלב 3 — Commits משמעותיים (10 דק')
בכל שלב עבודה הגיוני, ודאו שנוצר commit עם הודעה ברורה. אם ה-agent כתב הודעה גנרית — בקשו במפורש: *"כתוב מחדש את הודעת ה-commit האחרונה: מה השתנה ולמה, לא רק 'update'."*
בדקו את ההיסטוריה: `git log --oneline`.

### שלב 4 — PR מדומה (10 דק')
```bash
git diff main add-priority-feature
```
בקשו מכלי AI (אותו אחד או אחר): *"הנה ה-diff. כתוב תיאור PR קצר, ואז סקור את הקוד כ-reviewer — type hints? מקרי קצה? שמות ברורים?"*
קראו את התיאור והסקירה, תקנו אם צריך, ורק אז מזגו:
```bash
git checkout main
git merge add-priority-feature
```

### שלב 5 — סיכום (5 דק')
כתבו 3-4 משפטים: מה ה-agent עשה טוב לבד, איפה נדרשה התערבות שלכם, ואיך ה-Git history עוזר להבין את מה שקרה.

### קריטריוני הצלחה
- ✓ יש היסטוריית git עם לפחות 3 commits בעלי הודעות משמעותיות (לא "update"/"fix" גנרי).
- ✓ העבודה בוצעה בענף נפרד ומוזגה בסוף ל-main.
- ✓ יש תיאור PR + סקירת קוד שנכתבו בעזרת AI, ונקראו לפני המיזוג.
- ✓ תועד לפחות מקרה אחד שבו הלולאה (Plan→Act→Observe) "גילתה" בעיה תוך כדי עבודה.

### תוצר להגשה
קישור/צילום להיסטוריית ה-git (`git log --oneline`), תיאור ה-PR שנכתב, וסיכום 3-4 המשפטים משלב 5.

**בונוס:** נסו את אותה משימה פעם נוספת, הפעם ברמת אוטונומיה גבוהה יותר (בלי אישור על כל צעד). האם ההבדל בתוצאה — ובתחושת השליטה שלכם — היה משמעותי?
