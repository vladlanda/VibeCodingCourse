בסיום המפגש תוכלו:

1. להסביר, במונחי המנגנון ממפגש 2, למה ניסוח הפרומפט משנה את איכות הקוד — ולזהות "החלטות פתוחות" בפרומפט.

7. ליישם שלוש טכניקות משלימות: שאלות הבהרה, תוכנית לפני קוד, ותפקיד — ולדעת מה כל אחת **לא** עושה.

*(משך משוער: 4 דק')*

במפגש 2 ראינו שהמודל בונה תשובה טוקן אחר טוקן, ובכל צעד בוחר מתוך התפלגות של המשכים סבירים. ראינו גם שהזיות צפויות יותר כשהבקשה מעורפלת, כשחסר הקשר וכשאין גרסה מוגדרת.

מכאן נובעת התובנה של המפגש הזה: **הפרומפט הוא החלק היחיד בהתפלגות הזו שנמצא בשליטה שלכם.** כל מילה בפרומפט הופכת לחלק מההקשר שעליו המודל מתבסס. פרומפט מעורפל משאיר למודל הרבה המשכים "סבירים" שונים, והוא בוחר אחד מהם. פרומפט מדויק מצמצם את האפשרויות לאלה שאתם באמת רוצים.

פרומפט טוב לא פוטר מבדיקה. גם הפרומפט הכי טוב יכול להחזיר קוד עם באג או הזיה, ולכן העיקרון ממפגשים 1–2 נשאר: **קוראים, מריצים, בודקים.** מה שפרומפט טוב כן עושה: מקטין את מספר הסבבים עד לקוד תקין, ומקטין את מספר המקומות שבהם המודל צריך לנחש.

## חלק א' — המחשה: אותה מטרה, שני פרומפטים

*(משך משוער: 8 דק')*

### למה זה חשוב

לפני שלומדים כללים, צריך לראות שהבעיה אמיתית: שני פרומפטים לאותה מטרה, לאותו מודל, יכולים להחזיר קוד שאחד מהם שגוי והשני נכון. ההבדל הוא לא "מזל" — הוא הניסוח.

### דוגמה — הפרומפט החלש

```text
כתוב קוד לבדיקת מספר ראשוני
```

**פלט מייצג:**

```python
def is_prime(n):
    for i in range(2, n):
        if n % i == 0:
            return False
    return True
```

הקוד נראה הגיוני, וגם עובד על מספרים "רגילים". הנה מה שקורה כשמריצים אותו (פלט אמיתי):

```text
is_prime(97)  →  True     ✓
is_prime(9)   →  False    ✓
is_prime(2)   →  True     ✓
is_prime(1)   →  True     ✗  (1 אינו ראשוני)
is_prime(0)   →  True     ✗
is_prime(-7)  →  True     ✗
```

ויש בעיה נוספת: הלולאה רצה עד `n`. בדיקת המספר `1,000,003` לקחה 0.065 שניות; לפי אותו קצב, בדיקת `1,000,000,007` הייתה לוקחת **כ-65 שניות**. הפרומפט לא אמר שום דבר על יעילות, אז המודל בחר את הפתרון הכי פשוט.

### דוגמה — הפרומפט החזק

```text
כתוב פונקציה ב-Python בשם is_prime(n) שמקבלת מספר שלם ומחזירה True אם הוא ראשוני
ו-False אחרת.
- מספרים קטנים או שווים ל-1 (כולל 0 ושליליים) אינם ראשוניים.
- הפונקציה צריכה להיות יעילה גם למספרים בסדר גודל של מיליארד (בדיקה עד שורש n).
- בלי ספריות חיצוניות.
החזר: את הפונקציה עם type hints ו-docstring, ומתחתיה הסבר קצר בעברית.
```

**פלט מייצג:**

```python
import math

def is_prime(n: int) -> bool:
    """Return True if n is a prime number, False otherwise."""
    if n <= 1:
        return False
    if n <= 3:
        return True
    if n % 2 == 0:
        return False
    for d in range(3, math.isqrt(n) + 1, 2):
        if n % d == 0:
            return False
    return True
```

**פלט ההרצה (אמיתי):** `-7, 0, 1 → False` · `2, 3, 97, 7919 → True` · `4, 9, 91, 561 → False` · ו-`is_prime(1_000_000_007) → True` תוך **0.001 שניות**.

### מה לומדים מזה

אותו מודל, אותה מטרה. בפרומפט החלש המודל היה צריך לנחש: איזו שפה? מה עושים עם 1? כמה מהיר? הוא ניחש את "הפתרון הטיפוסי" — והטיפוסי לא טיפל במקרי הקצה. בפרומפט החזק לא נשארו ניחושים בנקודות האלה.

### טעות נפוצה

"הקוד רץ בלי שגיאה, אז הוא נכון." הפרומפט החלש החזיר קוד שרץ בלי שום הודעת שגיאה — ועדיין החזיר תשובה שגויה ל-1, ל-0 ולשליליים. קוד שרץ ≠ קוד נכון.

### Best practice

לפני ששולחים פרומפט, שאלו: **"אם שני מתכנתים שונים יקבלו את הבקשה הזו, האם הם יכתבו את אותה פונקציה?"** אם התשובה "לא" — הפרומפט משאיר ניחושים.

### בדקו את עצמכם

> הפרומפט החלש לא הזכיר מספרים שליליים, ובכל זאת הקוד "החליט" משהו לגביהם. מה הוא החליט, ולמה?
>
> *תשובה:* הוא החליט שהם ראשוניים (`True`), לא כי מישהו בחר בזה — אלא כי עבור n שלילי `range(2, n)` ריק, הלולאה לא רצה, והפונקציה מגיעה ל-`return True`. כשלא מגדירים התנהגות, היא נקבעת "במקרה" על ידי המימוש.

## חלק ב' — למה ניסוח משנה: "החלטות פתוחות"

*(משך משוער: 6 דק')*

### למה זה חשוב

כדי לשפר פרומפט בצורה שיטתית, ולא בניסוי וטעייה, צריך דרך למצוא מה חסר בו. הכלי לזה הוא ספירת "החלטות פתוחות".

### ההסבר

**פרומפט** הוא ההוראה שאתם נותנים למודל. כל משימת תכנות כוללת עשרות החלטות קטנות: שפה, שם פונקציה, סוג קלט, סוג פלט, מה עושים בקלט לא תקין, יעילות, ספריות, סגנון, ואיך להחזיר את התשובה. כל החלטה שלא כתבתם בפרומפט היא **החלטה פתוחה** — והמודל ממלא אותה בברירת המחדל הסבירה ביותר מנתוני האימון שלו. לפעמים ברירת המחדל מתאימה לכם, ולעיתים קרובות לא.

הכלל הוותיק של מדעי המחשב תקף גם כאן: **Garbage in → garbage out.** קלט מעורפל = פלט מעורפל.

### דוגמה — ספירת החלטות פתוחות

הפרומפט `"כתוב קוד לבדיקת מספר ראשוני"`:

| החלטה | נקבעה בפרומפט? | מה המודל עשה בפועל |
|---|---|---|
| שפה | לא | בחר Python (הנפוצה ביותר) |
| שם וחתימה | לא | `is_prime(n)` |
| מה מחזירים | לא | `True`/`False` |
| מקרי קצה (1, 0, שליליים) | לא | לא טיפל — שגוי |
| יעילות | לא | לולאה עד n — איטי מאוד במספרים גדולים |
| קלט מהמשתמש או פונקציה? | לא | פונקציה (לפעמים מודלים מוסיפים `input()`) |
| הסבר | לא | ללא |

**7 החלטות פתוחות** בפרומפט של 5 מילים. הפרומפט החזק מחלק א' סגר את כולן.

### טעות נפוצה

לחשוב שהפתרון הוא "פרומפט ארוך". פרומפט ארוך שמלא בנימוסים ובתיאורים כלליים ("אני צריך קוד ממש טוב ואיכותי בבקשה") לא סוגר אף החלטה. האורך לא משנה — מה שמשנה הוא כמה החלטות נסגרו.

### Best practice

לפני ששולחים פרומפט למשימה חשובה, רשמו לעצמכם 3–5 החלטות שאתם יודעים שחשובות לכם, ובדקו שכל אחת מהן כתובה בפרומפט.

### בדקו את עצמכם

> כמה החלטות פתוחות יש בפרומפט `"כתוב פונקציה שממיינת רשימה"`? מנו לפחות ארבע.
>
> *תשובה (חלק מהאפשרויות):* שפה; סדר עולה או יורד; האם לשנות את הרשימה המקורית או להחזיר חדשה; מה סוג האיברים (מספרים? מחרוזות?); מה עושים ברשימה ריקה; האם מותר להשתמש ב-`sort` המובנה.

## חלק ג' — ארבע אבני היסוד

*(משך משוער: 28 דק', כ-7 דק' לכל אבן יסוד)*

ארבע אבני היסוד הן דרך מסודרת לסגור החלטות פתוחות: **הקשר · מטרה · אילוצים · פורמט.** לא כל פרומפט קטן צריך את כל הארבע, אבל ככל שהמשימה חשובה או מורכבת יותר, כך כדאי לכלול יותר מהן. אפשר להשתמש בהן כרשימת תיוג: "נתתי הקשר? מטרה? אילוצים? פורמט?"

### 1. הקשר (Context)

#### למה זה חשוב

המודל לא יודע מה אתם בונים, למי, ובאיזו סביבה. בלי הקשר הוא מניח את המקרה הכללי — וקוד למקרה הכללי לרוב לא מתאים למקרה שלכם.

#### ההסבר

הקשר עונה על השאלות: **מה הפרויקט? מי ישתמש בזה? באיזו טכנולוגיה ובאיזו גרסה? אילו כללים עסקיים חלים?** הקשר טוב הוא קצר — משפט או שניים — וכולל רק מה שמשפיע על הקוד.

#### דוגמה עם קלט ופלט

**בלי הקשר:**
```text
כתוב פונקציה שמחשבת מחיר
```

**פלט מייצג:**
```python
def calculate_price(price, quantity):
    return price * quantity
```

המודל לא יודע שמדובר בחנות ישראלית עם מע"מ והנחות, אז הוא ניחש "מחיר × כמות". `calculate_price(100, 2)` מחזיר `200` — תשובה נכונה לשאלה שלא שאלתם.

**עם הקשר:**
```text
אני בונה מערכת קופה לחנות בישראל, ב-Python.
כתוב פונקציה final_price(base_price, discount_percent) שמחשבת את המחיר הסופי ללקוח:
קודם מורידים את ההנחה, ואז מוסיפים מע"מ של 18%. התוצאה בשקלים, מעוגלת לאגורות.
```

**פלט מייצג:**
```python
VAT_RATE = 0.18

def final_price(base_price: float, discount_percent: float = 0) -> float:
    if base_price < 0:
        raise ValueError("base_price must be non-negative")
    if not 0 <= discount_percent <= 100:
        raise ValueError("discount_percent must be between 0 and 100")
    discounted = base_price * (1 - discount_percent / 100)
    return round(discounted * (1 + VAT_RATE), 2)
```

**פלט ההרצה (אמיתי):**
```text
final_price(100, 10)   →  106.2
final_price(59.9)      →  70.68
final_price(250, 25)   →  221.25
final_price(100, 150)  →  ValueError: discount_percent must be between 0 and 100
```

ולמה "מעוגלת לאגורות" חשוב? בלי עיגול, אותו חישוב מחזיר `106.19999999999999` (זו לא טעות של המודל — כך מחשבים מייצגים שברים עשרוניים). משפט אחד בפרומפט חסך באג תצוגה בקופה.

#### טעות נפוצה

להניח שהמודל "יודע" כללים מקומיים. שיעור מע"מ, פורמט תאריך, מטבע, מספר טלפון — כל אלה משתנים בין מדינות ובין שנים (שיעור המע"מ בישראל, למשל, עלה מ-17% ל-18% בינואר 2025, ומודל שאומן על נתונים ישנים עלול להשתמש בערך הישן). כלל עסקי שלא כתבתם — המודל ינחש.

#### Best practice

פתחו פרומפט משמעותי במשפט "אני בונה ___ עבור ___ ב-___". ציינו במפורש כל כלל עסקי וכל מספר שהקוד תלוי בו.

#### בדקו את עצמכם

> כתבתם: `"כתוב פונקציה שבודקת אם תאריך הוא תאריך תקין"`. איזה משפט הקשר הכי חשוב להוסיף?
>
> *תשובה:* באיזה פורמט מגיע התאריך (למשל `DD/MM/YYYY` כמו בישראל, או `MM/DD/YYYY` כמו בארה"ב). בלי זה, `05/11/2026` יכול להתפרש כ-5 בנובמבר או כ-11 במאי.

### 2. מטרה (Goal)

#### למה זה חשוב

"תעזור לי עם הקוד" זו לא מטרה. מטרה מעורפלת מובילה לתשובה שעונה על פרשנות אחרת של הבקשה — ולעיתים קרובות אי אפשר לדעת את זה בלי להריץ.

#### ההסבר

מטרה טובה היא **משפט אחד שאומר מה ייווצר ומה הוא יעשה**. הדרך הכי חזקה לנסח מטרה היא לצרף לה **דוגמת קלט ← פלט צפוי**: דוגמה אחת סוגרת פרשנויות שמילים לא סוגרות.

#### דוגמה עם קלט ופלט

**מעורפל:**
```text
תעשה משהו עם הרשימה הזו כדי שלא יהיו בה כפילויות
```

לבקשה הזו יש שתי פרשנויות סבירות, ושני מימושים נכונים שמחזירים תוצאות שונות. על הקלט `[3, 1, 3, 2, 1]` (פלט אמיתי):

```text
sorted(set(x))           →  [1, 2, 3]     (ממוין, הסדר המקורי אבד)
list(dict.fromkeys(x))   →  [3, 1, 2]     (שומר את סדר ההופעה הראשונה)
```

שתי התשובות "מסירות כפילויות". רק אתם יודעים איזו מהן רציתם.

**ממוקד:**
```text
כתוב פונקציה ב-Python בשם remove_duplicates(items) שמסירה כפילויות מרשימה
ושומרת על סדר ההופעה הראשונה של כל איבר.
דוגמה: [3, 1, 3, 2, 1] → [3, 1, 2]
```

עכשיו יש רק תשובה נכונה אחת, והדוגמה גם משמשת אתכם לבדיקה: מריצים על `[3, 1, 3, 2, 1]` ומשווים ל-`[3, 1, 2]`.

#### טעות נפוצה

לשלב כמה מטרות במשפט אחד ("תסדר את הקוד, תוסיף פיצ'ר ותתקן את הבאג"). המודל יבצע את כולן חלקית. מטרה אחת לפרומפט; משימות נוספות — בצעדים נפרדים (חלק ח').

#### Best practice

נסחו את המטרה במשפט אחד, וצרפו דוגמת קלט ← פלט אחת לפחות. **אם קשה לכם לנסח את המטרה במשפט אחד — כנראה שגם לכם עוד לא ברור מה אתם רוצים.** זה הזמן לחשוב, לא לשלוח.

#### בדקו את עצמכם

> מה הבעיה במטרה `"כתוב פונקציה שמחזירה את הציון הגבוה"`? כתבו גרסה ממוקדת.
>
> *תשובה:* לא ברור מה הקלט (רשימת מספרים? מילון שם→ציון?) ומה מחזירים (את הציון? את שם הסטודנט? מה בתיקו?). גרסה ממוקדת: `"כתוב פונקציה top_student(grades) שמקבלת מילון {שם: ציון} ומחזירה את שם הסטודנט עם הציון הגבוה; בתיקו — השם הראשון לפי סדר המילון. דוגמה: {'דנה': 90, 'יוסי': 95} → 'יוסי'"`.

### 3. אילוצים (Constraints)

#### למה זה חשוב

אילוצים הם בדיוק מה שהמודל נוטה לפספס לבד: מקרי קצה, ספריות שמותר או אסור להשתמש בהן, גרסאות, מגבלות גודל. אלה גם המקומות שבהם קוד "שנראה נכון" נשבר בשימוש אמיתי.

#### ההסבר

שלושה סוגי אילוצים:

1. **טכניים** — שפה, גרסה, ספריות מותרות/אסורות. (`"Python 3.11, רק ספרייה סטנדרטית"`)
2. **התנהגותיים — מקרי קצה** — מה קורה בקלט ריק, שלילי, לא תקין, ענק. (`"ברשימה ריקה החזר None"`)
3. **סגנון והיקף** — אורך, שמות, מבנה. (`"עד 20 שורות, שמות משתנים באנגלית"`)

#### דוגמה עם קלט ופלט

**בלי אילוצים:**
```text
כתוב פונקציה שמחשבת ממוצע של רשימת מספרים
```

**פלט מייצג:**
```python
def average(nums):
    return sum(nums) / len(nums)
```

על רשימה ריקה (פלט אמיתי):
```text
average([])  →  ZeroDivisionError: division by zero
```

**עם אילוצים:**
```text
כתוב פונקציה ב-Python בשם average(numbers) שמחשבת ממוצע של רשימת מספרים.
אילוצים:
- רק ספרייה סטנדרטית.
- רשימה ריקה → החזר None (לא שגיאה).
- אם יש ברשימה ערך שאינו מספר → זרוק ValueError עם הודעה שמציינת את הערך הבעייתי.
```

**פלט מייצג:**
```python
def average(numbers):
    if not numbers:
        return None
    for x in numbers:
        if not isinstance(x, (int, float)) or isinstance(x, bool):
            raise ValueError(f"Non-numeric value: {x!r}")
    return sum(numbers) / len(numbers)
```

**פלט ההרצה (אמיתי):**
```text
average([])            →  None
average([90, 85, 77])  →  84.0
average([90, "85"])    →  ValueError: Non-numeric value: '85'
```

שימו לב לשורה `isinstance(x, bool)`: ב-Python, `True` נחשב מספר (`True + 1 == 2`). מודל טוב מוסיף את הבדיקה הזו — אבל אם לא הייתם מבקשים טיפול בערכים לא מספריים, לא הייתה בדיקה בכלל.

#### טעות נפוצה

אילוצים סותרים או עמוסים מדי: `"בלי ספריות, בלי לולאות, בשורה אחת, עם טיפול בכל מקרה קצה אפשרי ותיעוד מלא"`. המודל ינסה לספק את כולם, ויוותר בשקט על חלק מהם. עדיף 3–5 אילוצים שבאמת חשובים לכם.

#### Best practice

לכל פונקציה, שאלו את עצמכם שלוש שאלות וכתבו את התשובות כאילוצים: **מה קורה בקלט ריק? מה קורה בקלט לא תקין? אילו ספריות מותרות?**

#### בדקו את עצמכם

> ביקשתם פונקציה שקוראת קובץ, וקיבלתם קוד שמשתמש ב-`pandas`. אבל ב-Colab של הקורס זה עבד, ובשרת של הצוות `pandas` לא מותקן. איזה אילוץ היה מונע את זה?
>
> *תשובה:* אילוץ טכני על ספריות: `"רק ספרייה סטנדרטית של Python"` (או `"מותר להשתמש רק ב-csv וב-json"`).

### 4. פורמט (Format)

#### למה זה חשוב

הפורמט קובע כמה עבודה תצטרכו לעשות **אחרי** שהתשובה מגיעה: להעתיק ולהשתמש מיד, או לנקות הסברים, להסיר קוד מיותר ולהתאים למבנה של הקובץ שלכם.

#### ההסבר

פורמט עונה על: **מה בדיוק אני רוצה לקבל, ובאיזה מבנה?** קוד בלבד או קוד + הסבר? פונקציה אחת או קובץ שלם? עם דוגמת הרצה? באיזו שפה ההסבר?

#### דוגמה עם קלט ופלט

בקשה בלי פורמט, `"כתוב תוכנית שבודקת אם מספר זוגי"`, מחזירה לעיתים קרובות קוד כזה (פלט מייצג):

```python
n = int(input("Enter a number: "))
if n % 2 == 0:
    print("Even")
else:
    print("Odd")
```

זה עובד כתוכנית עצמאית — אבל אי אפשר לייבא את זה לפרויקט שלכם: כל `import` של הקובץ יעצור ויחכה לקלט מהמקלדת, ואין פונקציה שאפשר לקרוא לה.

אותה בקשה עם פורמט:
```text
כתוב פונקציה is_even(n) -> bool.
פורמט: רק הפונקציה, בלי input() ובלי print; אחריה 3 דוגמאות שימוש כהערות;
ומתחת לבלוק הקוד — הסבר של שני משפטים בעברית.
```

עכשיו מה שמתקבל הוא בדיוק החלק שנכנס לקוד שלכם.

**פורמטים שימושיים לקוד:**

| מה מבקשים | מתי |
|---|---|
| `"רק קוד, בלי הסבר"` | כשאתם מבינים את הנושא ורוצים להעתיק מהר |
| `"קוד + הסבר קצר בעברית"` | כשאתם לומדים |
| `"רק הפונקציה, בלי input/print"` | כשהקוד נכנס לפרויקט קיים |
| `"קוד + 3 דוגמאות הרצה עם הפלט הצפוי"` | כשאתם רוצים לבדוק מיד |
| `"רק את השורות ששונו, עם הסבר מה שונה"` | כשמתקנים קוד קיים ארוך |
| `"טבלה: אפשרות / יתרון / חיסרון"` | כשמבקשים להשוות פתרונות |

#### טעות נפוצה

לבקש "קובץ שלם" כשרוצים לשנות שלוש שורות. המודל עלול לכתוב מחדש את כל הקובץ — ולשנות בדרך דברים שלא ביקשתם. לתיקון קוד קיים, בקשו "רק את השינויים".

#### Best practice

החליטו מראש **איפה התשובה תיכנס** (קובץ קיים? קובץ חדש? רק לקריאה?), ובקשו פורמט שמתאים למקום הזה.

#### בדקו את עצמכם

> קיבלתם פונקציה מצוינת, אבל עם 40 שורות הסבר לפניה ואחריה, ואתם רק רוצים להדביק אותה. מה תוסיפו לפרומפט הבא?
>
> *תשובה:* הוראת פורמט: `"רק קוד, בלי הסבר"` (ואם צריך, `"בבלוק קוד אחד"`).

## חלק ד' — מרכיבים הכול: Before/After מלא ותבנית לשימוש חוזר

*(משך משוער: 7 דק')*

### למה זה חשוב

ארבע אבני היסוד שימושיות רק אם הן הופכות להרגל. הדרך להפוך אותן להרגל: תבנית קבועה שממלאים בכל פעם.

### דוגמה — Before/After

**Before:**
```text
כתוב לי קוד למחשבון
```

**After:**
```text
אני בונה מחשבון פשוט ב-Python לתרגיל בקורס מבוא.                        ← הקשר
כתוב פונקציה calculate(a, op, b) שמבצעת אחת מארבע פעולות: + - * /       ← מטרה
- חלוקה באפס → החזר את המחרוזת "שגיאה: חלוקה באפס" (לא לזרוק חריגה).     ← אילוצים
- פעולה שאינה אחת מהארבע → החזר "שגיאה: פעולה לא חוקית '<op>'".
- בלי ספריות, בלי input().
החזר: את הפונקציה, ואחריה 4 דוגמאות הרצה עם הפלט הצפוי, והסבר קצר בעברית.  ← פורמט
```

**פלט מייצג:**
```python
def calculate(a: float, op: str, b: float):
    if op == "+": return a + b
    if op == "-": return a - b
    if op == "*": return a * b
    if op == "/":
        if b == 0:
            return "שגיאה: חלוקה באפס"
        return a / b
    return f"שגיאה: פעולה לא חוקית '{op}'"
```

**פלט ההרצה (אמיתי):**
```text
calculate(6, "+", 2)  →  8
calculate(6, "/", 4)  →  1.5
calculate(6, "/", 0)  →  שגיאה: חלוקה באפס
calculate(6, "%", 2)  →  שגיאה: פעולה לא חוקית '%'
```

ה-After ארוך פי עשרה — וזו בדיוק הנקודה. דקה של ניסוח חוסכת סבבים של "לא, לא זה, תתקן".

### תבנית פרומפט לשימוש חוזר

שמרו את התבנית הזו (בקובץ טקסט, בפתק, איפה שנוח) והעתיקו אותה כשאתם מתחילים משימה חדשה:

```text
הקשר:   אני בונה ___ עבור ___, ב-___ (שפה + גרסה).
מטרה:   כתוב ___ (שם + חתימה) ש___.
        דוגמה: ___ → ___
אילוצים:
- ספריות: ___
- קלט ריק / לא תקין: ___
- ___
פורמט:  ___ (רק קוד / קוד + הסבר / רק השינויים / + דוגמאות הרצה)
```

### טעות נפוצה

למלא את התבנית בצורה מכנית גם למשימה של שורה אחת. לשאלה כמו "איך הופכים רשימה ב-Python?" לא צריך ארבעה סעיפים. התבנית היא למשימות שבהן לטעות יש מחיר.

### Best practice

השתמשו בתבנית לכל משימה שהקוד שלה נכנס לפרויקט או להגשה. שמרו את הפרומפטים שעבדו טוב ב-**Prompt Log** (ראו התרגול) — עם הזמן תצברו ספרייה אישית של פרומפטים מוכחים.

### בדקו את עצמכם

> באיזה סעיף של התבנית נכנסת ההוראה `"בלי input()"`? ובאיזה נכנס `"מע"מ 18%"`?
>
> *תשובה:* `"בלי input()"` — אילוצים (או פורמט; שתי התשובות סבירות, כי זו גם מגבלה טכנית וגם קובעת את מבנה התשובה). `"מע"מ 18%"` — הקשר (כלל עסקי של המערכת).

## חלק ה' — מבנה ותוחמים: פרומפט ארוך שהמודל לא מתבלבל בו

*(משך משוער: 6 דק')*

### למה זה חשוב

ברגע שמדביקים לפרומפט קוד, נתונים או הודעת שגיאה, הפרומפט מתערבב: איפה נגמרות ההוראות שלכם ומתחיל החומר? אם המודל לא יודע, הוא עלול להתייחס להערה בקוד כאל הוראה, או לחשוב שחלק מההוראות הוא חלק מהקוד.

### ההסבר

**תוחמים (delimiters)** הם סימנים שמפרידים בין חלקי הפרומפט. שלוש דרכים נפוצות, וכולן עובדות בכל הכלים המודרניים:

1. **כותרות Markdown** — `### הקשר`, `### קוד`, `### מה אני רוצה`.
2. **בלוקי קוד** — שלושה גרשיים הפוכים (```` ``` ````) לפני ואחרי הקוד.
3. **תגיות בסגנון XML** — `<code>...</code>`, `<error>...</error>`. אין בהן קסם; הן פשוט גבולות ברורים שקל למודל לזהות.

### דוגמה — בלי מבנה ועם מבנה

**בלי מבנה** (הכול בפסקה אחת):
```text
יש לי את הקוד הזה def total(prices): return sum(prices) # TODO: להוסיף מע"מ
והוא מחזיר מספר לא נכון תוכל לתקן ולהוסיף גם הנחה
```

לא ברור: האם "להוסיף מע"מ" הוא חלק מהבקשה או סתם הערה ישנה? מה "מספר לא נכון" — על איזה קלט? איזו הנחה?

**עם מבנה:**
````text
### הקשר
פונקציה ממערכת הקופה (Python 3.11). מע"מ 18%.

### הקוד הנוכחי
```python
def total(prices):
    return sum(prices)  # TODO: להוסיף מע"מ
```

### הבעיה
total([100, 50]) מחזיר 150. ציפיתי ל-177.0 (150 + מע"מ 18%).

### מה אני רוצה
1. תקן כך שהתוצאה כוללת מע"מ, מעוגלת לאגורות.
2. אל תוסיף הנחה בשלב הזה.
החזר רק את הפונקציה המתוקנת והסבר של משפט אחד.
````

עכשיו כל חלק מסומן, הקלט והפלט הצפוי כתובים במפורש, וההוראה "אל תוסיף הנחה" לא תתבלבל עם הקוד.

### טעות נפוצה

להדביק קובץ שלם של 500 שורות כשהבעיה בפונקציה אחת. זה ממלא את חלון ההקשר (מפגש 2, חלק ה'), ומקשה על המודל למצוא את הרלוונטי. ניהול הקשר בפרויקט גדול הוא הנושא של מפגש 4; לעת עתה — הדביקו רק את מה שנוגע לבעיה.

### Best practice

לכל פרומפט שכולל קוד או נתונים: **הוראות בכותרות, קוד בבלוק קוד, ודוגמת "קיבלתי X, ציפיתי ל-Y".**

### בדקו את עצמכם

> הדבקתם קוד עם ההערה `# don't change this function`, וביקשתם "תשפר את הקוד". המודל לא נגע בפונקציה הזו. למה?
>
> *תשובה:* כי הקוד והבקשה לא היו מופרדים, והמודל קרא את ההערה כחלק מההוראות. אם רציתם שהיא תשתנה — כתבו זאת במפורש בחלק "מה אני רוצה", מחוץ לבלוק הקוד.

## חלק ו' — איטרציה: לשפר בלולאה, ולהחזיר שגיאות בצורה נכונה

*(משך משוער: 10 דק')*

### למה זה חשוב

פרומפט מושלם מהניסיון הראשון הוא נדיר. הלולאה **פרומפט ← תוצאה ← הרצה ← שיפור** היא תהליך העבודה הרגיל, ושניים-שלושה סבבים הם הנורמה, לא כישלון. השאלה היא לא אם יהיו סבבים, אלא האם כל סבב מקדם אתכם.

### ההסבר

בכל סבב מוסיפים **בדיוק את מה שהתגלה כחסר**. כשהתגלתה שגיאה, הסבב הבא כולל שלושה דברים:

1. **הודעת השגיאה המלאה** (כל ה-traceback, לא "יש שגיאה").
2. **הקלט שגרם לה.**
3. **מה ציפיתם שיקרה.**

למה זה עובד? מנגנונית (מפגש 2): הודעת השגיאה מכילה את שם השורה, סוג השגיאה והסיבה. ההקשר הזה מחדד מאוד את ההתפלגות של המודל לכיוון התיקון הנכון. "לא עובד, תתקן" לא מוסיף שום מידע — המודל ינחש מה לא עבד.

### דוגמה — שלושה סבבים, עם שגיאות אמיתיות

**סבב 1:**
```text
כתוב פונקציה average(grades) שמחשבת ממוצע ציונים.
```
**פלט מייצג:** `return sum(grades) / len(grades)`. מריצים על הציונים שנקראו מקובץ — `["90", "85", "77"]` — ומקבלים (פלט אמיתי):

```text
Traceback (most recent call last):
  File "grades.py", line 4, in <module>
    average(["90", "85", "77"])
  File "grades.py", line 2, in average
    return sum(grades) / len(grades)
           ~~~^^^^^^^^
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

**סבב 2 — פרומפט טוב:**
```text
הרצתי את הפונקציה על ["90", "85", "77"] (הציונים נקראים מקובץ טקסט, ולכן הם מחרוזות)
וקיבלתי:
TypeError: unsupported operand type(s) for +: 'int' and 'str'
ציפיתי ל-84.0. תקן כך שהפונקציה תקבל ציונים כמחרוזות. רשימה ריקה → None.
```
**פלט מייצג:** ממיר כל ציון ל-`float` לפני החישוב. מריצים: `["90", "85", "77"] → 84.0` ✓. אבל בקובץ האמיתי יש שורה ריקה (תלמיד שלא נבחן):

```text
average(["90", "", "77"])  →  ValueError: could not convert string to float: ''
```

**סבב 3:**
```text
עובד, תודה. מקרה נוסף: בקובץ יש שורות ריקות או עם רווחים, למשל ["90", "", " 77 ", "85"].
שורה ריקה = תלמיד שלא נבחן ← יש לדלג עליה. רווחים בתחילת/סוף ציון ← להתעלם מהם.
אם אין אף ציון תקף ← None. ציון שאינו מספר (למשל "abc") ← שגיאה, כמו עכשיו.
עגל לשתי ספרות.
```

**פלט מייצג:**
```python
def average(grades):
    numbers = []
    for g in grades:
        g = g.strip()
        if g == "":
            continue
        numbers.append(float(g))
    if not numbers:
        return None
    return round(sum(numbers) / len(numbers), 2)
```

**פלט ההרצה (אמיתי):**
```text
average(["90", "", " 77 ", "85"])  →  84.0
average(["", ""])                  →  None
average(["90", "abc"])             →  ValueError: could not convert string to float: 'abc'
```

כל סבב הוסיף מקרה אחד שהתגלה בהרצה. לא ניחשנו מראש הכול, ולא כתבנו מחדש את כל הבקשה.

### מתי להפסיק לתקן ולהתחיל מחדש

אם אחרי 3–4 סבבים אותה בעיה חוזרת, או שהתיקונים שוברים דברים שכבר עבדו — פתחו **שיחה חדשה** עם פרומפט משופר שכולל את כל מה שלמדתם מהסבבים (כל מקרי הקצה שהתגלו). שיחה ארוכה עם ניסיונות כושלים ממלאת את ההקשר בקוד שגוי, והמודל ממשיך להיצמד אליו (מפגש 2, חלק ה').

### טעות נפוצה

`"לא עובד, תתקן"` / `"עדיין שגיאה"`. אין כאן מידע חדש, ולכן התיקון הוא ניחוש. לעיתים המודל "מתקן" משהו אחר לגמרי ושובר קוד תקין.

### Best practice

בכל סבב תיקון: **שגיאה מלאה + הקלט + הפלט הצפוי.** שינוי אחד לסבב. אחרי 3–4 סבבים בלי התקדמות — שיחה חדשה עם פרומפט מסכם. (דיבוג שיטתי של באגים קשים יותר — מפגש 9.)

### בדקו את עצמכם

> כתבו מחדש את הסבב הבא כך שיהיה שימושי: `"הקוד שנתת קורס, תסדר"`.
>
> *תשובה (דוגמה):* `"הרצתי את get_user(5) וקיבלתי KeyError: 'email' בשורה 12. המילון של משתמש 5 הוא {'name': 'דנה'} — בלי email. ציפיתי שהפונקציה תחזיר None לאימייל חסר במקום לקרוס."`

## חלק ז' — Few-shot: ללמד דרך דוגמאות

*(משך משוער: 9 דק')*

### למה זה חשוב

יש דברים שקשה מאוד להסביר במילים ופשוט מאוד להראות: פורמט פלט, סגנון שמות, כללי המרה. דוגמה אחת או שתיים עושות את העבודה של פסקת הסבר — ובונוס: הן גם בדיקה מוכנה.

### ההסבר

**Few-shot** = מצרפים לפרומפט כמה דוגמאות של קלט ← פלט, והמודל מזהה את הדפוס וממשיך אותו. מנגנונית (מפגש 2) זה טבעי: המודל ממשיך דפוסים שהוא רואה בהקשר, ודוגמאות הן הדפוס הכי ברור שאפשר לתת. היכולת הזו תוארה לראשונה בהרחבה במאמר של GPT-3 (Brown et al., 2020).

**מונחים:** **Zero-shot** — בלי דוגמאות. **One-shot** — דוגמה אחת. **Few-shot** — 2–5 דוגמאות, בדרך כלל המדויק ביותר.

### דוגמה 1 — דפוס פשוט (המרה לשם קבוע)

```text
המר תיאור לשם קבוע בסגנון Python:
"user name"        → USER_NAME
"max retry count"  → MAX_RETRY_COUNT
"default time out" →
```

**פלט:** `DEFAULT_TIME_OUT`. לא הסברנו את הכלל ("אותיות גדולות, רווח הופך לקו תחתון") — המודל הסיק אותו מהדוגמאות.

### דוגמה 2 — דוגמאות כמפרט לפונקציה

נניח שאתם צריכים פונקציה שמנרמלת מספרי טלפון ישראליים מטופס הרשמה. להסביר במילים את כל הכללים (מקפים, סוגריים, רווחים, קידומת 972, האפס המוביל) — ארוך ומבלבל. במקום זה:

```text
כתוב פונקציה ב-Python בשם normalize_phone(raw) שמנרמלת מספר טלפון ישראלי
לפורמט בינלאומי. דוגמאות:
"050-1234567"       → "+972501234567"
"(03) 123-4567"     → "+97231234567"
"+972 50 123 4567"  → "+972501234567"
"0501234567"        → "+972501234567"
"12345"             → ValueError (מספר לא תקין)
רק ספרייה סטנדרטית.
```

**פלט מייצג:**
```python
import re

def normalize_phone(raw: str) -> str:
    digits = re.sub(r"\D", "", raw)
    if digits.startswith("972"):
        digits = digits[3:]
    if digits.startswith("0"):
        digits = digits[1:]
    if len(digits) not in (8, 9):
        raise ValueError(f"Invalid Israeli phone number: {raw!r}")
    return "+972" + digits
```

**פלט ההרצה (אמיתי) — על הדוגמאות מהפרומפט:**
```text
050-1234567       → +972501234567   ✓
(03) 123-4567     → +97231234567    ✓
+972 50 123 4567  → +972501234567   ✓
0501234567        → +972501234567   ✓
12345             → ValueError: Invalid Israeli phone number: '12345'   ✓
```

הדוגמאות שימשו פעמיים: פעם כ**מפרט** למודל, ופעם כ**בדיקה** שלכם. (הרעיון של "דוגמאות כבדיקות" הוא הבסיס לטסטים אוטומטיים — מפגש 8.)

### טעות נפוצה

1. **דוגמאות דומות מדי.** אם כל הדוגמאות הן `"05X-XXXXXXX"`, המודל עלול לכתוב פונקציה שעובדת רק על הפורמט הזה. בחרו דוגמאות **שונות זו מזו**, כולל מקרה קצה ומקרה שגוי.
2. **דוגמאות שסותרות זו את זו** — המודל יבחר כלל אחד, ולא תדעו איזה.
3. **לא להריץ את הדוגמאות.** few-shot לא מבטיח שהקוד יעבור על הדוגמאות שנתתם — חייבים לבדוק.

### Best practice

2–5 דוגמאות, מגוונות, שכוללות לפחות מקרה קצה אחד ומקרה שגוי אחד. אחרי שהקוד מגיע — **הריצו אותו על אותן דוגמאות.**

### בדקו את עצמכם

> רוצים פונקציה שממירה תאריך מ-`"2026-10-15"` ל-`"15/10/2026"`. נתתם דוגמה אחת בלבד. איזו דוגמה שנייה תוסיפו כדי שהמודל לא יטעה, ולמה?
>
> *תשובה:* דוגמה שבה היום והחודש שונים בבירור ואחד מהם קטן מ-10, למשל `"2026-03-07" → "07/03/2026"`. היא מבהירה גם את הסדר (יום/חודש ולא חודש/יום) וגם שיש אפס מוביל.

## חלק ח' — פירוק משימה גדולה לצעדים

*(משך משוער: 10 דק')*

### למה זה חשוב

בקשה כמו `"תבנה לי אפליקציית מטלות"` כוללת עשרות החלטות פתוחות בבת אחת. המודל מייצר טוקן אחר טוקן ולא "מתכנן פרויקט" (מפגש 2), ולכן ככל שהתשובה ארוכה יותר — גדל הסיכוי לטעות באמצע, ולכם קשה יותר למצוא אותה. משימה מפורקת = צעדים קטנים שכל אחד נבדק לבד.

### ההסבר

שלבי העבודה:
1. **פרקו** את המשימה ל-3–6 צעדים, שכל אחד מהם מייצר משהו שאפשר להריץ ולבדוק.
2. **בקשו צעד אחד** בכל פרומפט.
3. **הריצו ובדקו** את הצעד לפני שממשיכים.
4. בצעד הבא — ציינו מה כבר קיים (או הדביקו אותו), כדי שהמודל יבנה עליו ולא מחדש.

אפשר גם **לבקש מהמודל לפרק** — אבל לבדוק את הפירוק לפני שמתחילים:

```text
אני רוצה לבנות אפליקציית מטלות פשוטה ב-Python (שורת פקודה, בלי ממשק גרפי).
אל תכתוב קוד עדיין. פרק את המשימה ל-4 עד 6 צעדים, כך שכל צעד מייצר פונקציה
שאפשר להריץ ולבדוק לבד. לכל צעד: שם הפונקציה ומה היא עושה, במשפט אחד.
```

**פלט מייצג:**
```text
1. make_task(title, due_date) — יוצרת מילון שמייצג מטלה אחת.
2. add_task(tasks, title, due_date) — מוסיפה מטלה חדשה לרשימה.
3. show_tasks(tasks) — מדפיסה את המטלות הפתוחות לפי תאריך יעד.
4. complete_task(tasks, title) — מסמנת מטלה כהושלמה.
5. main() — לולאת תפריט שמחברת את הכול.
```

### דוגמה — ביצוע הצעדים, עם בדיקה בין צעד לצעד

**צעד 1:**
```text
כתוב פונקציה make_task(title, due_date) שמחזירה מילון שמייצג מטלה:
title (מחרוזת), done (בהתחלה False), due_date (אובייקט datetime.date).
```
```python
def make_task(title: str, due_date: date) -> dict:
    return {"title": title, "done": False, "due_date": due_date}
```
**בדיקה (פלט אמיתי):** `make_task("להגיש תרגיל", date(2026, 11, 5))` ← `{'title': 'להגיש תרגיל', 'done': False, 'due_date': datetime.date(2026, 11, 5)}` ✓

**צעד 2:**
```text
יש לי כבר את make_task (מצורפת למטה). עכשיו כתוב add_task(tasks, title, due_date)
שמוסיפה מטלה לרשימה tasks בעזרת make_task. כותרת ריקה או רק רווחים → ValueError.
<הדבקת make_task>
```
```python
def add_task(tasks: list, title: str, due_date: date) -> None:
    if not title.strip():
        raise ValueError("title must not be empty")
    tasks.append(make_task(title.strip(), due_date))
```
**בדיקה (פלט אמיתי):** אחרי שתי הוספות `len(tasks) → 2` ✓; `add_task(tasks, "  ", ...)` ← `ValueError: title must not be empty` ✓

**צעד 3:**
```text
עכשיו כתוב show_tasks(tasks) שמדפיסה רק את המטלות שלא הושלמו, ממוינות לפי
תאריך יעד, בפורמט: YYYY-MM-DD  כותרת. אם אין מטלות פתוחות — "אין מטלות פתוחות".
```
```python
def show_tasks(tasks: list) -> None:
    open_tasks = [t for t in tasks if not t["done"]]
    if not open_tasks:
        print("אין מטלות פתוחות")
        return
    for t in sorted(open_tasks, key=lambda t: t["due_date"]):
        print(f"{t['due_date'].isoformat()}  {t['title']}")
```
**בדיקה (פלט אמיתי)** — הוספנו "להגיש תרגיל" (5.11) ואחריה "לקרוא פרק 3" (1.11):
```text
2026-11-01  לקרוא פרק 3
2026-11-05  להגיש תרגיל
```
המיון לפי תאריך עובד, למרות שסדר ההוספה היה הפוך ✓

**צעד 4 (`complete_task`)** — באותה שיטה. אחרי `complete_task(tasks, "לקרוא פרק 3") → True`, הפונקציה `show_tasks` מדפיסה רק את `2026-11-05  להגיש תרגיל` ✓, ו-`complete_task(tasks, "לא קיים") → False` ✓.

אם משהו היה נשבר בצעד 3, ידענו בדיוק איפה לחפש: ב-8 השורות של `show_tasks`, ולא ב-60 שורות של "אפליקציה שלמה".

### טעות נפוצה

1. **צעדים גדולים מדי** — "צעד 1: כל הלוגיקה; צעד 2: הממשק". זה לא פירוק.
2. **לא לבדוק בין הצעדים** — מבקשים את כל הצעדים ברצף ומריצים רק בסוף. כך חוזרים לבעיה המקורית.
3. **לא לציין מה כבר קיים** — המודל כותב מחדש את `make_task` בצעד 2, בגרסה קצת שונה, ועכשיו יש שתיים.

### Best practice

**צעד = משהו שאפשר להריץ ולבדוק.** בין צעדים: מריצים, מאמתים, ורק אז ממשיכים. בכל צעד מציינים את מה שכבר קיים.

### בדקו את עצמכם

> פירקתם משימה כך: "1. לכתוב את הקוד. 2. לבדוק את הקוד. 3. לתקן באגים." מה הבעיה בפירוק הזה?
>
> *תשובה:* זה פירוק של **תהליך העבודה**, לא של **המשימה**. כל הקוד עדיין נכתב בצעד אחד. פירוק נכון מחלק את המוצר עצמו לחלקים (פונקציות/רכיבים) שכל אחד מהם נכתב ונבדק בנפרד.

## דמו חי — משפרים פרומפט יחד

*(משך משוער: 10 דק')*

**המטרה:** לראות בזמן אמת איך כל אבן יסוד משנה את התוצאה.

**פרומפט פתיחה:**
```text
כתוב קוד למשחק ניחוש מספר
```

**צעדי הדמו:**
1. **הריצו כמו שהוא.** לפני שקוראים את הקוד, ספרו בקול את ההחלטות הפתוחות (חלק ב'): שפה? טווח? כמה ניסיונות? מה קורה בקלט לא מספרי? — ואז ראו מה המודל החליט בכל אחת.
2. **הוסיפו הקשר + מטרה:**
   ```text
   ב-Python, כתוב משחק ניחוש מספר בשורת הפקודה: המחשב בוחר מספר אקראי בין 1 ל-100,
   והמשתמש מנחש. אחרי כל ניחוש הצג "גבוה מדי" או "נמוך מדי", עד שמנחשים נכון.
   ```
   הריצו. נסו להקליד `abc` — מה קורה? (ברוב המקרים: `ValueError: invalid literal for int() with base 10: 'abc'` והמשחק קורס.)
3. **הוסיפו אילוצים + פורמט:**
   ```text
   ...הגבל ל-7 ניסיונות והצג כמה נותרו. אם הקלט אינו מספר או מחוץ לטווח 1–100 —
   הצג הודעה ידידותית ובקש שוב, בלי להוריד ניסיון. בסוף הצג "ניצחת ב-X ניסיונות"
   או "המספר היה Y". החזר: קוד בלבד, ואחריו הסבר של 3 משפטים בעברית.
   ```
4. **השוו** את שתי הגרסאות: מה השתנה בין 5 מילים לפרומפט מלא? הקלידו שוב `abc`, `0`, `101`.
5. **סבב איטרציה:** מצאו בעיה אחת שנשארה (אם אין — בקשו "בסוף המשחק שאל אם לשחק שוב") ונסחו סבב תיקון לפי חלק ו'.

**אם אתם לומדים לבד:** עשו את הדמו בעצמכם ושמרו את שלוש גרסאות הפרומפט עם התוצאה של כל אחת. זה בדיוק הפורמט של התרגול.

## חלק ט' — שלוש טכניקות משלימות

*(משך משוער: 10 דק')*

### 1. בקשו מהמודל לשאול שאלות הבהרה

#### למה ואיך

כשאתם עצמכם לא בטוחים מה כל ההחלטות הפתוחות, תנו למודל למצוא אותן. במקום שהמודל ינחש — הוא שואל.

#### דוגמה

```text
אני רוצה לכתוב מערכת לניהול ספריית ספרים קטנה ב-Python.
לפני שאתה כותב קוד — שאל אותי עד 6 שאלות על מה שאתה צריך לדעת כדי לכתוב אותה נכון.
אל תכתוב קוד עד שאענה.
```

**פלט מייצג:**
```text
1. אילו פעולות נדרשות? (הוספת ספר, חיפוש, השאלה, החזרה, מחיקה?)
2. אילו פרטים לשמור על כל ספר? (כותר, מחבר, שנה, ISBN?)
3. האם יש מנויים שמשאילים, ואם כן — מגבלה על מספר ספרים לאדם?
4. האם הנתונים צריכים להישמר בין הרצות (קובץ), או רק בזיכרון?
5. ממשק: שורת פקודה, או רק פונקציות שתקראו להן מקוד אחר?
6. מה קורה כשמנסים להשאיל ספר שכבר מושאל?
```

כל שאלה כאן היא החלטה פתוחה שהייתם משאירים לניחוש. עונים, ורק אז מבקשים את הקוד (רצוי בפירוק לצעדים — חלק ח').

#### מה זה לא עושה

המודל לא תמיד ישאל את **כל** השאלות החשובות. השאלות שלו הן נקודת התחלה; אתם מוסיפים את מה שחסר.

### 2. תוכנית לפני קוד

#### למה ואיך

לבעיות עם לוגיקה לא טריוויאלית, בקשו מהמודל לתאר תוכנית קצרה לפני הקוד. המחקר על **Chain of Thought** (Wei et al., 2022) הראה שבקשה מהמודל לפרט שלבי ביניים משפרת ביצועים בבעיות שדורשות כמה צעדי חשיבה. היתרון הגדול לכם: **אפשר לבדוק את התוכנית לפני שקוראים 30 שורות קוד.** תוכנית שגויה קל לתפוס במשפט אחד.

#### דוגמה

```text
כתוב פונקציה שממיינת רשימת מספרים בלי להשתמש ב-sort או sorted.
לפני הקוד, תאר את התוכנית ב-3–4 משפטים. אחר כך כתוב את הקוד. אל תשנה את הרשימה המקורית.
```

**פלט מייצג — התוכנית:**
```text
אעתיק את הרשימה כדי לא לשנות את המקור. אעבור על הרשימה ואשווה כל שני איברים סמוכים;
אם הם בסדר הפוך — אחליף ביניהם. אחזור על המעבר עד שעובר סבב שלם בלי אף החלפה
(Bubble Sort). אחרי כל מעבר, האיבר הגדול ביותר כבר במקומו, אז אפשר לקצר את הטווח.
```

**הקוד:**
```python
def bubble_sort(items):
    result = list(items)
    n = len(result)
    swapped = True
    while swapped:
        swapped = False
        for i in range(n - 1):
            if result[i] > result[i + 1]:
                result[i], result[i + 1] = result[i + 1], result[i]
                swapped = True
        n -= 1
    return result
```

**פלט ההרצה (אמיתי):** `[5, 2, 9, 1, 5] → [1, 2, 5, 5, 9]` · `[] → []` · `[1] → [1]`

אפשר לבדוק שהקוד עושה את מה שהתוכנית אמרה: העתקה (`list(items)`), השוואת שכנים, עצירה כשאין החלפות, וקיצור הטווח (`n -= 1`).

#### מה זה לא עושה

חלק מהמודלים העדכניים ("מודלי חשיבה") כבר מתכננים פנימית לפני שהם עונים. גם אז הבקשה לתוכנית כתובה שימושית — לא בשביל המודל, אלא **בשבילכם**: כדי לבדוק את הגישה לפני הקוד.

### 3. תפקיד (Role Prompting)

#### למה ואיך

פתיחה כמו `"אתה מפתח Python בכיר שמקפיד על קוד נקי"` משנה את **סגנון** התשובה: יותר type hints, יותר docstrings, יותר טיפול בשגיאות, טון מקצועי יותר.

#### דוגמה

```text
אתה מרצה שמסביר לסטודנטים בשנה ראשונה. הסבר מה עושה הקוד הבא, שורה אחר שורה,
בלי מונחים שלא הוסברו קודם:
<הקוד>
```
לעומת אותה בקשה עם `"אתה מפתח בכיר שעושה code review"`. הראשונה תחזיר הסבר איטי ומפורט; השנייה — הערות קצרות על בעיות ושיפורים. אותו קוד, שני סוגי תשובות שונים לגמרי.

#### מה זה לא עושה

תפקיד **לא** הופך את המודל לחכם יותר ולא מוסיף לו ידע. מחקר שבדק 162 תפקידים שונים על 2,410 שאלות עובדתיות, בארבע משפחות של מודלים, מצא שהוספת תפקיד בהנחיית המערכת לא שיפרה את הדיוק באופן עקבי (Zheng et al., 2024). "אתה מומחה אבטחה" לא ימנע הזיות בקוד אבטחה. השתמשו בתפקיד כדי לכוון **סגנון וקהל יעד**, ובאבני היסוד כדי לכוון **תוכן**.

### טעות נפוצה (לשלוש הטכניקות)

להשתמש בהן במקום ארבע אבני היסוד. "אתה מומחה עולמי, חשוב צעד אחר צעד" + `"כתוב קוד למחשבון"` עדיין משאיר את כל ההחלטות הפתוחות. הטכניקות האלה **מוסיפות** על פרומפט טוב — הן לא מחליפות אותו.

### Best practice

- **לא בטוחים מה צריך?** ← שאלות הבהרה.
- **הלוגיקה מסובכת?** ← תוכנית לפני קוד, ובדיקה של התוכנית.
- **רוצים סגנון או רמת הסבר מסוימת?** ← תפקיד.

### בדקו את עצמכם

> סטודנט כתב: `"אתה מומחה Python עם 20 שנות ניסיון. כתוב פונקציה שמתחברת ל-API של מזג אוויר."` וקיבל קוד עם פונקציה שלא קיימת בספרייה. למה התפקיד לא עזר, ומה היה עוזר?
>
> *תשובה:* תפקיד משנה סגנון, לא ידע — המודל עדיין מנבא טוקנים סבירים ויכול להזות. מה שהיה עוזר: הקשר ואילוצים (איזה API בדיוק, איזו ספרייה ובאיזו גרסה, צירוף קטע מהתיעוד), ואחרי זה — בדיקה מול התיעוד והרצה (מפגש 2).

## סיכום

*(משך משוער: 4 דק')*

| נושא | במשפט אחד | מה עושים בפועל |
|---|---|---|
| החלטות פתוחות | כל מה שלא כתבתם — המודל מנחש | סופרים לפני ששולחים |
| הקשר | מה, למי, באיזו טכנולוגיה, אילו כללים | "אני בונה ___ עבור ___ ב-___" |
| מטרה | משפט אחד + דוגמה | "דוגמה: X → Y" |
| אילוצים | ספריות, מקרי קצה, היקף | "קלט ריק ← ___; קלט לא תקין ← ___" |

| Few-shot | דוגמאות = מפרט + בדיקה | 2–5 דוגמאות מגוונות, ואז להריץ עליהן |
| פירוק | צעד = משהו שאפשר להריץ | בודקים בין צעד לצעד |
| טכניקות משלימות | שאלות / תוכנית / תפקיד | מוסיפים על פרומפט טוב, לא במקומו |

| Prompt Engineering | ניסוח שיטתי של פרומפטים כדי לקבל פלט מדויק ושימושי |
| החלטה פתוחה | החלטה על הקוד שלא נקבעה בפרומפט, ולכן המודל ממלא אותה בברירת מחדל |
| הקשר (Context) | רקע: מה בונים, למי, באיזו טכנולוגיה, אילו כללים עסקיים |
| אילוץ (Constraint) | כלל או גבול שהפתרון חייב לעמוד בו (ספריות, מקרי קצה, היקף) |
| מקרה קצה (Edge case) | קלט חריג — ריק, שלילי, ענק, לא תקין — שבו קוד נוטה להישבר |
| תוחם (Delimiter) | סימן שמפריד בין חלקי פרומפט (כותרת, בלוק קוד, תגית) |
| איטרציה (Iteration) | שיפור הדרגתי של פרומפט או קוד בסבבים |
| Traceback | הודעת השגיאה המלאה של Python, כולל השורה והסיבה |
| Zero-shot / One-shot / Few-shot | פרומפט עם 0 / 1 / כמה דוגמאות קלט ← פלט |
| פירוק משימה (Task decomposition) | חלוקת משימה גדולה לצעדים קטנים שכל אחד נבדק לבד |
| Chain of Thought | בקשה מהמודל לפרט שלבי חשיבה או תוכנית לפני התשובה |
| Role prompting | פתיחת הפרומפט בתפקיד ("אתה ___") כדי לכוון סגנון וקהל יעד |
| Prompt Log | תיעוד אישי של פרומפטים: לפני, אחרי, תוצאה ומה שיפר |
